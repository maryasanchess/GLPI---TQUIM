RELATÓRIO DE OCORRÊNCIAS EM EXCEL (GLPI)
=========================================

O QUE FAZ
- exportar_relatorio_ocorrencias.py: busca os chamados de uma entidade no
  GLPI do ano corrente (via API de busca) e gera um arquivo .xlsx formatado,
  com uma aba "Anual" (todos os chamados do ano) e uma aba por mês que tiver
  ao menos um chamado — campos nativos do chamado + campos personalizados do
  plugin Fields. Não altera nada no GLPI: é só leitura.
- enviar_relatorio.php: envia esse arquivo por e-mail, reaproveitando a
  configuração de e-mail já existente no GLPI (a mesma usada pelas
  notificações) — não precisa de credenciais SMTP próprias.
- notificar_ocorrencia.php: roda em polling (via cron, a cada poucos
  minutos), detecta chamados novos numa entidade e envia um e-mail já
  preenchido com os valores reais dos campos do plugin Fields, no layout do
  Comunicado de Ocorrência — o GLPI não permite isso nas notificações
  nativas (campos de plugin não têm tag disponível). Também define o
  cabeçalho Message-ID no mesmo formato usado pelo GLPI, para que respostas
  por e-mail sejam reconhecidas pelo Coletor de E-mails e virem
  acompanhamento no chamado.
- criar_dashboard_ocorrencias.php: cria um Dashboard novo reaproveitando os
  cards do modelo padrão "Assistência" do GLPI (Dashboard::getDefaults()),
  removendo os que não fazem sentido fora de um contexto de suporte de TI
  (Problemas, Mudanças, Chamados Recorrentes, por Entidade, por Tipo de
  Requisição) e destacando o card de Categoria. Só precisa rodar uma vez.
- configurar_categorias_grupos_classificacao.php: reorganiza as categorias
  de Ocorrências em pai/filho (ex.: Manutenção > Elétrica/Mecânica/Predial),
  cria os grupos por unidade (Ocorrências Armazém, Ocorrências SJP), cria o
  bloco "Classificação da Qualidade" (código do Quadro 1 da Qualidade) e deixa a
  Data de abertura automática/travada como no template de TI. Só precisa
  rodar uma vez — e tem um passo manual obrigatório antes (ver comentário no
  topo do script): o bloco da Qualidade precisa ser criado pela tela do
  GLPI, não pela API (bug conhecido do plugin Fields).
- exportar_avaliacao_motoristas.py: gera a base do relatório de avaliação de
  motoristas — lista as ocorrências que a Qualidade já classificou (bloco
  "Classificação da Qualidade" preenchido) E que foram marcadas para entrar
  na avaliação, uma aba com tudo e outra com contagem por motorista. Ainda
  não calcula desconto de pontos (falta a tabela da Qualidade dizendo quanto
  cada código tira). Busca os campos de plugin direto da tabela do plugin
  Fields, não pelo /search/Ticket — pedir muitas colunas de plugin de uma
  vez na busca nativa deixa o GLPI lento a ponto de travar (testado).
- verificar_solicitacao_relatorio.php: permite pedir o relatório de
  Ocorrências por e-mail, fora do dia agendado do mês. Manda um e-mail pra
  chamados.ti@tquim.com.br com "RELATORIO OCORRENCIAS" no assunto, de um
  endereço autorizado, e o relatório do ano corrente volta por e-mail pra
  quem pediu. NÃO lê a caixa de e-mail diretamente (tentamos com a extensão
  imap do PHP, mas essa versão do GLPI usa uma biblioteca PHP pura pra
  e-mail, incompatível, e o pacote do sistema nem tinha candidato de
  instalação). Em vez disso, deixa o PRÓPRIO coletor de e-mail nativo do
  GLPI (já testado, já funciona) transformar o e-mail-gatilho num chamado
  normal, e roda em polling (via cron, mesmo padrão do
  notificar_ocorrencia.php) procurando chamados novos com esse assunto, em
  qualquer entidade. Ao achar um chamado de remetente autorizado: gera e
  manda o relatório, depois fecha o chamado com um comentário. De remetente
  não autorizado: fica aberto, sem resposta automática, pra alguém olhar.

ANTES DE USAR (exportar_relatorio_ocorrencias.py)
1. Copie config_exemplo.json para config.json e preencha api_url, app_token
   e user_token.
2. Instale a dependência: pip install openpyxl
   (em servidores com Python gerenciado pelo sistema, pode ser necessário
   pip install --break-system-packages openpyxl, ou usar um ambiente
   virtual — instale com o mesmo `python3` que vai rodar o script, ex.:
   python3 -m pip install --break-system-packages openpyxl)
3. Ajuste a constante ENTITY_OCORRENCIAS e a lista PLUGIN_COLUMNS no topo
   do script para a entidade e os IDs de campo do seu GLPI (os IDs de
   campo do plugin Fields aparecem em Configurar > Listas suspensas, ou
   via /listSearchOptions/Ticket na API).

COMO USAR
    python exportar_relatorio_ocorrencias.py [caminho_saida.xlsx] [ano]
Sem argumento, salva na pasta atual com o nome Relatorio_Ocorrencias_<ano>.xlsx
(ano corrente por padrão).

ANTES DE USAR (enviar_relatorio.php)
1. Ajuste os caminhos dos dois require_once no topo do script para onde o
   GLPI está instalado no seu servidor (raiz do GLPI).
2. Edite a lista $destinatarios com os e-mails que devem receber o relatório.
3. Deve ser executado com o mesmo usuário do servidor web (ex.: www-data),
   não com um usuário comum — é ele quem tem acesso ao ambiente do GLPI
   (banco, configuração, log de erros).

COMO USAR
    sudo -u www-data php enviar_relatorio.php <caminho_do_arquivo.xlsx>

ANTES DE USAR (notificar_ocorrencia.php)
1. Ajuste os caminhos dos require_once, a constante ENTIDADE_OCORRENCIAS, a
   lista $destinatarios e os nomes de tabela/coluna do plugin Fields (mesma
   observação do exportar_relatorio_ocorrencias.py) no topo do script.
2. Também deve ser executado como o usuário do servidor web.
3. Na primeira execução, para não notificar retroativamente todos os
   chamados já existentes na entidade, inicialize o arquivo de estado com o
   maior ID de chamado já existente:
     echo "<maior id atual>" > ultimo_id.txt

COMO USAR (manual, pra testar)
    sudo -u www-data php notificar_ocorrencia.php

AGENDADO (a cada 5 minutos) — NÃO coloque isso no crontab de um usuário
comum chamando "sudo -u www-data ...". Cron nunca tem terminal, então esse
sudo falha sempre com "a terminal is required to authenticate" — e se o
servidor não tiver um serviço de e-mail local instalado, esse erro some sem
deixar rastro em lugar nenhum (foi exatamente o que aconteceu na TQUIM: o
cron rodava, o sudo falhava calado, e nenhum e-mail saía, sem nenhum erro
visível). Em vez disso:

1. Garanta que notificacao.log e ultimo_id.txt sejam do dono www-data:
     sudo touch notificacao.log
     sudo chown www-data:www-data notificacao.log ultimo_id.txt
   (sem isso, o próprio ">> notificacao.log" falha silenciosamente antes do
   PHP rodar, porque só o dono/grupo do arquivo tem permissão de escrita.)

2. Coloque o agendamento direto no crontab do PRÓPRIO www-data (roda nativo,
   sem precisar de sudo nem senha depois de configurado):
     sudo crontab -u www-data -e
   e adicione a linha (sem "sudo -u www-data" — já é o dono):
     */5 * * * * cd /caminho/para/relatorio_ocorrencias && php notificar_ocorrencia.php >> notificacao.log 2>&1

3. Confira que pegou: sudo crontab -u www-data -l
   E depois de alguns minutos: tail notificacao.log (deve ter "Enviado: ..."
   quando houver chamado novo, ou nada se não houver nada pra notificar —
   mas o arquivo deve continuar existindo e acessível, e a data de
   modificação dele deve avançar a cada execução).

ANTES DE USAR (verificar_solicitacao_relatorio.php)
1. Ajuste os caminhos dos require_once no topo do script para onde o GLPI
   está instalado no seu servidor (raiz do GLPI).
2. Ajuste a lista $remetentesAutorizados com os e-mails que podem pedir o
   relatório por e-mail (precisa ser o e-mail de um usuário já cadastrado no
   GLPI, já que o requerente do chamado é resolvido por lá).
3. Deve ser executado como o usuário do servidor web (mesma observação do
   notificar_ocorrencia.php).
4. Na primeira execução, pra não processar retroativamente algum chamado
   antigo que por acaso tenha esse texto no título, inicialize o arquivo de
   estado com o maior ID de chamado já existente (em qualquer entidade), já
   com o dono certo:
     echo "<maior id atual>" | sudo tee ultimo_id_solicitacao.txt
     sudo chown www-data:www-data ultimo_id_solicitacao.txt
5. Este script chama o exportar_relatorio_ocorrencias.py por baixo, só que
   rodando como www-data (não como o usuário comum que só roda o mensal
   agendado) - por isso precisa de mais 3 ajustes de permissão que só esse
   caminho de execução precisa:
     a) instalar o openpyxl pro Python que o www-data usa (instalar só pro
        seu próprio usuário, com --user, não é visível pro www-data):
          sudo /usr/bin/python3 -m pip install --break-system-packages openpyxl
     b) o www-data precisa conseguir LER o config.json (que por padrão é
        600, só o dono lê):
          sudo chgrp www-data config.json && sudo chmod 640 config.json
     c) o www-data precisa conseguir ESCREVER na pasta (pra salvar o .xlsx
        gerado na hora):
          sudo chgrp www-data . && sudo chmod g+w .

COMO USAR (manual, pra testar)
    sudo -u www-data php verificar_solicitacao_relatorio.php

AGENDADO: mesma observação do notificar_ocorrencia.php - coloque no crontab
do PRÓPRIO www-data, não chame com "sudo -u www-data" de outro usuário e
garanta que solicitacao_relatorio.log e ultimo_id_solicitacao.txt sejam do
dono www-data antes de agendar:
    */5 * * * * cd /caminho/para/relatorio_ocorrencias && php verificar_solicitacao_relatorio.php >> solicitacao_relatorio.log 2>&1

ANTES DE USAR (criar_dashboard_ocorrencias.php)
Ajuste $dashboardKey e o nome do dashboard no topo do script, se quiser.

COMO USAR
    sudo -u www-data php criar_dashboard_ocorrencias.php
Depois, troque a entidade ativa para a entidade em questão antes de abrir o
dashboard — o GLPI não tem um jeito nativo de travar um dashboard numa
entidade fixa; os cards sempre respeitam a entidade ativa de quem está
vendo.

AGENDAR EXECUÇÃO AUTOMÁTICA (mensal, em um servidor Linux sempre ligado)
1. Crie um cliente de API dedicado a essa automação em
   Configurar > Geral > API (restrinja o IP permitido ao próprio
   servidor, separado do cliente usado para uso interativo). O app_token só
   aparece uma vez na tela no momento em que é gerado — não é possível
   recuperá-lo depois, nem pelo banco de dados nem pela API.
2. Copie os dois scripts e o config.json para o servidor (ex.:
   ~/relatorio_ocorrencias/) e restrinja a permissão do config.json:
   chmod 600 config.json
3. Se a pasta do script ficar dentro do home de um usuário comum (ex.:
   /home/usuario/relatorio_ocorrencias), dê ao usuário do servidor web
   permissão para *atravessar* essa pasta home (sem isso, o PHP não
   consegue abrir o arquivo gerado, mesmo com o arquivo em si acessível):
   chmod o+x /home/usuario
4. Adicione ao crontab (dia 1º de cada mês, às 8h):
     crontab -e
   e acrescente a linha (ajuste os caminhos):
     0 8 1 * * cd /caminho/para/relatorio_ocorrencias && /usr/bin/python3 exportar_relatorio_ocorrencias.py >> relatorio.log 2>&1 && sudo -u www-data php enviar_relatorio.php Relatorio_Ocorrencias_$(date +\%Y).xlsx >> relatorio.log 2>&1

OBSERVAÇÕES
- O token de API (app_token) e o token pessoal (user_token) só são
  exibidos uma vez, no momento em que são gerados/regenerados na
  interface do GLPI. Não é possível recuperá-los depois — nem pelo banco
  de dados nem pela API.
- enviar_relatorio.php usa a classe interna GLPIMailer do GLPI (o mesmo
  bootstrap usado por front/cron.php), lendo o remetente padrão
  (Config core: admin_email / admin_email_name) — não é necessário
  informar usuário/senha de SMTP em nenhum lugar deste projeto.
